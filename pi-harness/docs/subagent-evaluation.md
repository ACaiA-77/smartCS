# Subagent 评估（Phase 8 §8.3）

> **结论先行**：**维持单 Main Agent，不引入 Subagent。** 当前 7 工具面的隔离收益（≈180 token/轮）低于一次子会话交接的成本（实测基线提示 ≥300 token），且当前**不存在**计划 §22 预设的"RAG prompt 与交易 prompt 严重冲突"——pi 只有一份系统提示词，域知识经工具与上下文进入，不靠相互竞争的提示词。**触发重估的条件**已量化为曲线：声明工具面超过 ~15 个（或域提示词真的分叉）时，隔离收益才可能超过交接成本。
>
> **不落地任何代码**；本文与两个可复跑脚本即为交付物。

## 1. 方法（可复跑）

测量的是**生产装配本身**发往模型的请求：`createSmartCsAgent`（`toolMode: "business"`，Faux provider 只替换模型）+ 该轮的 system prompt 与工具声明（取自 provider 收到的 `toolsAdded`）。token 计数用 tiktoken `cl100k_base`——与运行时上下文预算同一编码。

```bash
npx tsx scripts/phase8-subagent-eval.ts > .runtime/phase8/subagent-eval.json
python scripts/phase8-count-tokens.py .runtime/phase8/subagent-eval.json
```

配置：`full`（现状全部 READ 工具）／`specialist`（只声明本域工具）／`full+8`、`full+23`（同一场景下人为扩面到 13、28 个声明工具）。场景：RAG 密集型（政策问答）与交易密集型（订单/退款）。

## 3. 判读

1. **没有"提示词冲突"可解**：两域共用同一份 557 token 的系统提示词，域差异全部落在工具声明与上下文注入上。计划 §22 的触发条件"RAG prompt 与交易 prompt 严重冲突"在当前架构下**不成立**——分上下文不会消除任何提示词冲突，只会减少无关工具声明。
2. **隔离收益有下限地小**：当前 5 工具面下，分域最多省 168–187 token/轮。而一次子会话交接至少要付出「父会话的委派轮（自身 prompt 557 + 工具 + 委派说明）」+「子会话的结果摘要」——即便按最省的 300 token 估算，**也在当前面上亏**。
3. **成本曲线是线性的**：工具声明按 ≈103 token/个增长，没有规模效应。所以问题会在工具面扩张时**突然**变得显著：13 个声明工具时单轮 1 766（其中 1 181 是工具），28 个时 3 315（2 730 是工具）——此时把一个交易轮交给只声明 3 个工具的专家，省下的是 ~2 543 token，交接成本才开始被覆盖。
4. **触发条件（建议写进后续阶段的门槛）**：
   - 声明工具面 **> ~15 个**：隔离收益（≈1 000+ token/轮）开始超过交接成本；
   - 或者出现**真正的提示词分叉**（例如两个域需要互相矛盾的风格/合规指令）——那时单提示词无法同时满足，分上下文是唯一解；
   - 或者需要**独立记忆/权限边界**（子会话作为权限隔离单元），那是安全需求而非 token 需求，另行评估。

## 4. 建议

- **维持单 Main Agent**（现状）。工具面继续走"白名单即工具面"的显式路线（Phase 8 §8.1 已验证：未列入白名单的工具不会声明），扩张必须是有意的。
- **Phase 9/终局**：若 READ 工具面继续增长（每加一个 ≈103 token/轮×每轮），在**接近 15 个声明工具**时重跑本评估的脚本（一条命令，离线），用当时的真实数字决定是否拆分；不要凭直觉拆。
- **不要**为了"整齐"按域拆分子会话：当前面上它是负收益。

## 5. 局限（诚实边界）

- 场景样本为两类各一条真实装配请求，非统计样本；结论依赖的是**确定的成本结构**（线性工具声明 + 共用提示词），不是抽样分布。
- 子会话交接成本用的是保守估计（≥300 token），未做真实委派实现的测量——因为本阶段**不落地** Subagent（设计 §8.3 明确"只出报告"）。若将来要落地，第一步应是把交接成本也变成实测项。
- Faux 模型不改变 token 计数（计数发生在请求内容上，与模型无关），故离线可复跑。
