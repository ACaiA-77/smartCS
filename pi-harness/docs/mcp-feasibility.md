# 4 个身份绑定工具的 MCP 可行性评估（Phase 8 §8.1 / P8-4）

> **结论**：**不迁移。** `order_query` / `ticket_query` / `refund_evaluate` / `risk_check` 继续走 HTTP 薄壳（`/internal/tools/execute`）是**合法终态**，不是欠债。MCP 只适合**无 per-user 数据**的读面（本阶段落地的 `knowledge_search` 即此类）。
>
> 本文只报告、不落地（设计 §8.1）。

## 1. 为什么身份不能进 MCP 通道（结构性原因）

| 事实 | 出处 | 后果 |
|---|---|---|
| MCP 连接是**长驻**的、按 **server** 鉴权（header/OAuth），连接建立时确定凭据 | pi 1.0.1 `McpServerConfig`（`headers`/`oauth`/`auth`）；MCP 规范 | 同一连接会服务**多用户、多轮次**，连接级凭据无法表达"本轮是谁" |
| 本项目的身份是**每轮信封**：`account_id`/`business_user_id`/`session_id`/`client_request_id`/`agent_run_id`/`tool_call_id`/`traceparent` | `src/business/turn-context.ts` + `PythonInternalClient` 全部 internal 调用 | 身份是 **per-call** 的，而 MCP 的连接是 **per-server** 的——这是范式错配，不是实现细节 |
| 身份必须由运行时从**服务令牌 claim** 强制绑定，工具参数里的 `user_id` 一律被剥离/覆盖 | `internal_api/tools.py`（`require_business_user_id` + 参数重绑）；Phase 2 D5 | 任何"把身份放进调用参数"的方案都会直接违反该不变量 |
| 审计/授权/幂等（`pending_action`、执行账本、回执）全部以**每轮身份 + tool_call_id** 为键 | Phase 5 授权服务、`execution_ledger`、`agent_run_receipt` | 身份一旦不可信，两阶段写与幂等链一起失效 |

## 2. 三条路线逐条评估

### 方案 A：TS 侧 wrapper 注入身份

MCP 工具对模型表现为无身份参数，TS 在调用前后补上身份（例如给 MCP server 传一个由运行时签发的短时凭据）。

- **安全性**：不改善。身份仍由 TS 持有并注入，运行时仍必须验证——即"能做的检查一个没少"，只是多了一跳。
- **复杂度**：**增加**。多一层 wrapper（模型 → MCP 工具 → wrapper → 运行时），且 wrapper 必须重新实现本已存在的服务令牌签发/传播；`agent_run_id`/`tool_call_id`/`traceparent` 的传播要在 MCP 协议里另找载体。
- **运维**：多一个可部署单元与一条链路要排障；MCP 的传输错误与运行时的业务错误语义不同，错误映射要重写一遍。
- **结论**：**净增复杂度、零安全收益**。否决。

### 方案 B：每用户（或每轮）一条 MCP 连接

把身份放进连接头，一个用户/一轮一条连接。

- **安全性**：可行但脆弱——凭据落到长驻连接上，连接池、空闲回收、异常重连都要保证"连接不会串到别人身上"；一旦复用出错就是跨用户越权，属于最难测的一类缺陷。
- **复杂度**：**高**。连接生命周期/池化/失效处理全部自建；且因为 `agent_run_id`/`tool_call_id` 是 **per-call** 的，实际上是"每轮一条连接" = 用 MCP 重新发明一遍 HTTP 请求，同时还丢了 HTTP 的成熟语义（超时/重试/幂等头）。
- **运维**：连接数随并发用户线性增长，MCP server 需要鉴权缓存与吊销机制；凭据轮换要覆盖所有活跃连接。
- **结论**：**用更贵的机制换取与现状等价的能力**。否决。

### 方案 C：身份放进工具参数

让模型把 `user_id` 等作为参数传给 MCP 工具。

- **安全性**：**直接违反核心不变量**——身份来自模型输出即可被提示注入伪造，等于把 Phase 2 D5 的强制绑定（以及"模型给的 user_id 是惰性的"这条验收）整体作废。
- **复杂度**：实现最省，代价是把安全模型换掉。
- **结论**：**立即否决**，记录在案以免后人重走。

## 3. 判读与建议

1. **判据是"这个工具的数据是否按用户分区"**，而不是"它是不是一个函数调用"。共享语料（`knowledge_search`）可 MCP 化；按用户分区的读/写（4 个工具 + 写工具）留在 HTTP 薄壳。
2. **HTTP 薄壳是合法终态**：它已经承载了每轮身份、服务令牌、审计、授权与幂等；把身份绑定的工具搬进一个**按连接鉴权**的协议，只会把已验证的语义重新实现一遍。
3. **若未来仍要统一到 MCP**，唯一自洽的方向是让 MCP **服务端**成为运行时的一部分（例如运行时直接暴露 MCP server，凭据与授权仍由运行时掌握，且为每次调用定义身份载体）——那是协议层的设计工作，不是本阶段的一次重构；届时方案 A/B/C 都需要重新评估。

## 4. 附：本阶段实际落地项的边界（对照）

`knowledge_search` 之所以可迁移，是因为它满足三条：① 共享语料、无 per-user 分区（现实现里也不在强绑身份的集合内）；② 只读、无副作用，因而不参与两阶段写/幂等链；③ 它的调用仍经过 pi 的 `tool_call`/`tool_result` 钩子（审计不缺位）。这三条同时成立才构成"可 MCP 化"的充分条件——4 个身份绑定工具都不满足第 ① 条。
