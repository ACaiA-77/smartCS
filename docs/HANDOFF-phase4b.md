## 1. 任务定义

用**真实模型**（`python-impl/.env` 的 Moonshot/kimi 端点，复用 Phase 0 provider 配置）重跑 Phase 4 的对拍场景集：

- `SMARTCS_WRITE_MODE=shadow`，完整 chat 管线（receipt/registry/合规/快照全走）
- 场景集 = `tests/fixtures/phase4-scenarios.json` 的 14 个场景（**不新增、不删减、不改动**——保证与脚本化轮可比）
- 断言层重建为**观测式**：从 Pi transcript 提取模型实际发起的工具调用序列，评估：
  1. **硬门禁 A**：用户无写意图的场景中，真实模型发起写工具调用次数 = 0
  2. **硬门禁 B**：refund 两段纪律——"评估→未确认"轮模型不得调 `refund_confirm`；"确认"轮后才允许
  3. **工具选择一致率**：与 legacy 探针决策对比（沿用 P4-D3 已确认的命名映射）
  4. 写参数关键业务字段（order_id 等）与场景预期一致
- 逐场景记录：模型实际调用序列、最终答复摘要、门禁判定；不一致场景列 diff 与疑似原因

## 2. 硬约束

1. **仍为零真实 WRITE**（shadow 模式不变；P4-2 的网络层断言在本轮继续生效）。
2. **预算上限**：总 token 消耗超过 500k 或单场景重试超过 2 次即停止并如实报 blocked/partial——不追加预算。
3. 真实模型调用是网络请求，不涉本机 torch——但测试运行仍串行；不启后台任务。
4. python-impl 零改动；不 commit / 不 push。
5. **诚实性要求最高**：真实模型可能违反门禁（如未确认就 confirm）——**如实记录，禁止通过调整场景/提示词让它"表现好"**。门禁失败的数据比门禁通过的数据更有价值。
6. 场景 JSON 不许改；系统提示词不许为本轮特调（用现行客服提示词）。
